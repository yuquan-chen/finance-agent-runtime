# 产品方向与 PRD 收敛摘要

> 状态：历史产品/阶段规划。当前实现边界以根目录 [README.md](../README.md) 和 [current-architecture.md](current-architecture.md) 为准。

> 更新日期：2026-08-21  
> 本文记录已经达成的产品判断，作为后续 PRD、交互设计和技术拆分的共同依据；不是详细接口设计。

## 1. 产品是什么

这是一个建立在现有统一 Payments API 之上的、面向跨境支付客户的 **AI 驱动支付运营平台**（AI-native payment operations layer / 客户操作台）。

它不是 BI 报表工具，不是单纯客服，也不应被定位成泛化的“财务 Agent”。它不自行清算、持有资金或替代支付核心系统；资金动作仍由底层统一 Payments API 和支付通道完成。平台负责把原本复杂的后台页面、表单、流程和接口，变成客户可自然发起和管理的操作入口。

一句话：

> 客户不必理解复杂的支付后台；通过对话和 `@` 业务对象即可完成跨境支付业务动作，并看到每一步的依据、状态和授权边界。

## 2. 服务对象与核心问题

### 主要用户

- 跨境支付平台的客户及其财务、运营人员。
- 后续也可服务平台内部运营、风控和客户支持人员，但产品主体首先是“客户”。

### 要解决的问题

客户通常需要在多个支付后台、账户页面和交易列表之间来回确认：钱在哪里、付款是否成功、某笔交易为何失败、某个公司 KYC 到哪一步、哪些账户或交易异常。字段和流程复杂，客户不应被迫学习内部系统结构。

Agent 应把这类任务收敛为：理解“我是谁、我能看什么、我想做什么”，再以受控方式查询或操作。

## 3. 核心能力地图

| 功能域 | 客户能做什么 | 底层依赖 |
|---|---|---|
| 收款人管理 | 添加、查询、修改、校验收款人 | Beneficiary API、KYC / 合规 API |
| 转账与付款 | 发起跨境付款、批量付款、保存草稿、再次付款 | Payment / Transfer API |
| 审批与授权 | 按角色审批付款、二次确认、限额控制 | 权限、风控、审批 API |
| 交易生命周期 | 查状态、取消、补件、处理失败、追踪到账 | Transaction、Channel、Webhook API |
| 资金与对账 | 查余额、流水、费用、汇率、对账单 | Account、Ledger、FX、Statement API |

AI、`@` 和自然语言是这套操作台的交互方式，不是产品本体。例如“给 `@SupplierA` 支付 3,000 USD”会被平台拆成付款账户、收款人、币种金额、汇率费用、通道、合规限额、提交与确认等受控步骤；统一 Payments API 仍是唯一真实执行入口。

BI、数据分析与故障解释属于辅助能力：它们帮助客户判断“该不该付、为什么失败、钱在哪里、成本是否异常”，但不取代上述支付业务主流程。

## 4. 身份、权限与数据边界

“我”不是由 LLM 从文字中猜出的概念，而是登录后的认证身份、所属组织、角色与授权范围。

```text
登录用户
  → 所属客户组织 / 角色 / 账户范围
  → 统一 Payments API 的授权请求范围
  → Agent 可查询、可引用、可操作的业务对象
```

- 统一 Payments API 是资金、账户和交易操作的业务入口与事实来源。
- 产品数据库（例如 Supabase）适合保存用户、组织、会话、授权、审计和产品配置；不是让前端或 LLM 直接持有支付系统最高权限的通道。
- 真正的付款操作必须经过身份、权限、参数确认、审批（如需要）和 API 审计，不能由普通对话直接执行。

## 5. 当前落地模块：Finance Agent

现有 Finance Agent 不是整个产品的定位，而是未来“支付操作助手”的大脑与受控数据层。它负责在客户询问、修改或执行前理解意图、查询必要事实，并提供可解释的状态与分析；它不替代统一 API 做资金动作。

当前先落地它，是为了把“客户提出问题”安全地变成“可校验、可执行、可解释的只读查询”，并为后续付款草稿、审批与状态处理复用同一套意图、权限、确认和审计边界。

### 用户体验目标

1. 用户用自然语言提出问题，例如“统计 Company 11 每个交易状态有多少笔”。
2. Agent 说明分析意图，系统生成并校验内部查询方法。
3. 只读校验通过后，系统自动执行查询并展示结果与解释。
4. 执行状态和结果在刷新后仍能按原消息顺序恢复；只对未来有副作用的动作保留确认卡。
5. 用户可修改方法；修改会生成新的卡片版本，旧卡保留修改状态与审计线索。

### 查询生成与安全原则

```text
业务意图 / 能力选择
  → 受控 Schema 候选搜索
  → 模型选择需要的表
  → 展开真实字段与关系
  → 生成 SQL
  → 系统校验与沙箱预检
  → 只读校验通过后自动执行
```

- 首轮模型不接收全量 173 张表。
- 模型只能从后端返回的候选表中选择，并且 SQL 只能使用随后展开的真实字段与关系。
- 用户筛选值在 SQL 规划阶段以不透明占位符表示；真实值仅在后端绑定。
- 校验失败时，系统可带结构化错误重新检索 Schema、重新规划；不让模型盲猜字段。
- 真实结果属于私有数据，不进入普通对话上下文；普通上下文只保存脱敏意图、结构和摘要。
- SQL 通过静态校验和沙箱预检后自动执行只读查询；当前只读链路不生成用户确认卡。

相关实现说明见 [README](../README.md)、[元数据规格](metadata_catalog_spec.md)、[方法与沙箱流程](method_draft_and_sandbox_flow.md)。

## 6. 当前范围与非目标

### 当前要做好

- 查询意图理解、Schema 选择、字段/关系约束与 SQL 正确性。
- 查询方法校验、版本持久化、刷新恢复和审计。
- 清晰的数据结果、趋势和解释展示。
- 真实只读数据源与稳定沙箱接入。

### 当前不做

- 不先做泛化的代码执行 Agent。
- 不让 LLM 直接读全量数据库 Schema、真实结果行或高权限密钥。
- 不在缺少身份、权限、确认与审批的情况下直接付款或转账。
- 不把支付执行能力和当前查询 MVP 混在同一个未受控流程里。

## 7. 阶段路线图

### 阶段 A：受控数据层与可信查询（现在）

目标：让客户提出一个查询后，系统能稳定地选对业务对象、表、字段和关系，生成可审查 SQL，并在校验通过后返回可信结果。

近期重点：

- 接入可用的 PostgreSQL 只读数据源和预检沙箱。
- 建立真实 Schema 查询回归集：客户、付款、交易、KYC、时间范围、连续追问。
- 补全表关系、业务别名、时间语义与状态口径。
- 完善确认卡、结果卡与查询失败时的可解释反馈。

### 阶段 B：收款人、付款草稿与支付操作台

目标：让已认证客户通过对话和 `@` 业务对象组织付款动作，而不绕过现有支付系统。

- 引入用户、组织、角色、账户范围和权限校验。
- 实现 `@账户`、`@收款人`、`@付款`、`@交易` 等可解析对象。
- 支持创建付款草稿、参数补齐、费用/风险提示与再次付款。
- 统一通过 Payments API 查询、校验并发起操作；真实执行仍由 API 完成。

### 阶段 C：审批、交易生命周期与异常闭环

目标：把“看见问题”升级为“定位、处理、跟踪和留痕”。

- 角色审批、二次确认、限额和风控校验。
- 失败付款、取消、退款/冲正、KYC 补件和账户异常的诊断与下一步建议。
- Webhook 状态更新、通知、工单和客户支持协作。
- 在权限范围内主动提示异常、到期事项和状态变化。

## 8. 成功标准

查询 MVP 是否成立，不看模型说得是否流畅，而看：

- SQL 是否只使用真实、授权且已展开的表和字段。
- 查询是否正确绑定用户输入，且不会泄露给普通模型上下文。
- 确认卡、执行结果和修改历史是否能刷新恢复并可审计。
- 用户是否能理解“将查询什么、为什么、何时执行、结果来自哪里”。
- 真实数据接入后，典型业务问题的表/字段/关联选择正确率是否可持续评估和提升。

## 9. 技术方案可行性与开源框架借鉴

### 结论

方案可行，但不应把产品做成一个能任意执行代码、任意调用内部系统的通用 Agent。适合的形态是：**受控支付工具编排器**。模型理解意图并提出下一步；确定性的后端策略、身份授权和统一 Payments API 决定它实际能看到什么、调用什么、何时必须由人确认。

现有 FastAPI + LangGraph + TableRegistry + 方法确认卡的实现可以继续作为阶段 A 的基础，不需要为了“Agent 化”而立即迁移到 Cloudflare Workers、Durable Objects 或 Codex SDK。后续可按部署和产品需要替换基础设施，但支付权限、操作卡、审计和 API 网关必须是独立于模型与框架的领域层。

### 可借鉴的部分

| 参考 | 可借鉴的原则 | 在本产品中的落地 |
|---|---|---|
| Cloudflare OS | 通过窄能力网关连接外部系统；每次访问绑定资源范围、授权、审计和人工确认 | 为 Payments API 建立服务端 `Payment Gateway`：按用户、组织、账户和操作类型签发受限调用，不把高权限密钥交给前端或 LLM |
| Cloudflare OS | 有状态工作区与可恢复的长流程 | 将会话、付款草稿、审批请求和执行事件持久化；刷新、Webhook 和多端打开后恢复同一笔业务操作 |
| Codex Agent / SDK | Agent loop、结构化输出、可恢复线程、工具调用与结果分离 | 保留 LangGraph 状态机；所有工具返回结构化领域对象，而不是让模型从自由文本猜执行结果 |
| Codex Symphony | 用明确的工作流、状态和审计来管理长任务，而不是依赖某一轮对话 | 将“草稿 → 校验 → 报价 → 审批 → 提交 → 状态追踪”建模为可审计状态机；它不是让多个 Agent 自主付款 |

Cloudflare OS 的 Gatekeeper 思路尤其值得借鉴：外部资源访问由专门网关包装，网关负责 OAuth/授权、最小资源范围、审计和副作用操作的人类确认。[Cloudflare OS README](https://github.com/cloudflare/cloudflare-os) 将这一层用于 Agent 与应用访问外部服务。Codex 的公开 Agent 实现、SDK 的结构化输出与可恢复线程，也说明“Agent harness”和业务应用可以分离；其 SDK 不是支付工作流引擎本身。[OpenAI Codex 公告](https://openai.com/index/codex-now-generally-available/)

Symphony 更像一个编排参考：它将任务状态和人工审阅放进外部工作流控制面，并通过 Codex App Server 驱动执行。[Symphony 说明](https://openai.com/index/open-source-codex-orchestration-symphony/) 我们可借鉴“状态机优先、可恢复、可审计”，但不应把 Linear 式任务编排或多 Coding Agent 直接搬到客户支付路径。

### 不应照搬的部分

- **不使用通用 Code Mode 执行支付动作。** Cloudflare OS 的通用 Agent 会写并运行代码，适合生产力工具和 Gadget；支付 API 调用必须是预定义、版本化、可审核的领域工具。
- **不让 LLM 持有或选择高权限凭据。** LLM 只能提出 `create_payment_draft`、`get_quote`、`submit_for_approval` 等受控意图；服务端网关根据已认证用户授权请求。
- **不把“模型调用工具成功”当作“支付成功”。** 付款提交、通道处理、到账必须由 API 响应、Webhook 和交易状态机确认。
- **不为当前查询 MVP 过早引入多 Agent、通用插件市场或动态代码沙箱。** 这些会扩大权限面、调试面和成本，却不能首先解决支付正确性。

### 目标技术架构

```text
客户 Web / App
  → 登录身份、组织、角色与账户范围
  → Payment Operations Agent（会话与状态机）
       ├─ 受控查询工具：Schema / 账户 / 交易 / KYC / 对账
       ├─ 支付领域工具：收款人、草稿、报价、合规、审批、提交、取消、状态
       ├─ Policy Engine：权限、限额、风控、必经确认、幂等与字段脱敏
       └─ Audit / Event Store：操作卡、审批、API 请求引用、Webhook 与状态变化
  → Payment Gateway（服务端）
  → 统一 Payments API / KYC / 风控 / 通道 / Webhook
```

其中 Payment Gateway 是最关键的边界：它接收的是后端验证后的结构化命令，而不是模型自由生成的 HTTP 请求。每个命令都应有明确输入 schema、资源范围、幂等键、风险等级、是否需要确认、是否需要审批，以及可用于恢复的操作引用。

### 一笔付款的推荐状态机

```text
用户意图
  → payment_draft（补齐收款人、账户、币种、金额）
  → validate（收款人 / KYC / 限额 / 路由资格）
  → quote（汇率、费用、预计到账）
  → review（客户确认）
  → approval_pending（如角色或金额要求审批）
  → submitted（调用统一 Payments API，携带幂等键）
  → processing / completed / failed / cancelled
```

Webhook 更新只能推进由后端维护的状态机；它不应由模型文本直接改变。模型在每个状态只负责解释、提示缺失信息、提出下一步受控动作。

### 可行性的前提条件

在开始阶段 B 前，需要确认统一 Payments API 至少能提供：

1. **资源模型与权限边界**：用户所属组织、账户、收款人、付款和交易的稳定 ID，以及可映射到产品角色的授权模型。
2. **可拆分操作**：创建/修改收款人、创建草稿、校验、报价、提交、取消、查询状态等独立接口，而不是一个不可恢复的大型“付款”接口。
3. **幂等与可追踪性**：提交操作支持 idempotency key、request ID、可查询状态和可靠 Webhook。
4. **合规与审批结果**：KYC、制裁筛查、限额、风险命中和审批状态可以作为结构化结果返回。
5. **可测试环境**：Sandbox 或模拟账户，可用于 API contract test、状态机回归和失败场景演练。

如果这些前提具备，技术风险主要不在“LLM 能否调用 API”，而在权限映射、支付状态一致性、异常恢复和审计设计；这些都可通过领域网关与状态机用常规工程方式控制。

### 推荐实施顺序

1. 完成阶段 A 的真实查询、回归评估和稳定审计；不要把资金执行接入当前通用 SQL 流程。
2. 先做只创建不提交的 `Beneficiary` 与 `Payment Draft` 工具，验证身份、权限、`@` 对象、字段补齐和确认卡。
3. 接入报价、合规校验与审批，再接入幂等提交和 Webhook 状态恢复。
4. 为每个领域工具建立 API contract test、权限测试、失败恢复测试和人工确认审计，而不是只评估自然语言回复质量。

## 10. 现有 Finance Agent 的接入准备度与升级清单

### 当前可直接复用的基础

| 已有能力 | 可复用方式 |
|---|---|
| LangGraph 状态编排 | 继续作为对话、确认、恢复和异常分支的编排层 |
| 方法确认卡、修改历史与刷新恢复 | 演进为付款草稿、报价和提交确认卡；保留版本和用户操作时间线 |
| 私有结果与普通上下文分离 | 支付明细、账户数据、报价和合规信息继续保持私有，不进入普通模型上下文 |
| Schema / 字段约束与参数脱值 | 用于只读事实查询、`@` 对象解析前的受控查找和支付前事实核验 |
| 审计日志与方法校验 | 演进为不可抵赖的操作事件、策略决定和 API 调用引用 |

### 当前不能直接用于支付的边界

| 缺口 | 当前情况 | 接支付 API 前必须补足 |
|---|---|---|
| 身份与租户 | `/v1/runs` 只接收问题和 `session_id`；会话是本地 JSON 文件 | 服务端认证中间件；`ActorContext(user_id, organization_id, roles, permitted_accounts)`；所有工具强制带此上下文 |
| 领域工具 | operation registry 目前只有 SQL / code 分析能力 | 独立定义 Beneficiary、Payment Draft、Quote、Compliance、Approval、Submit、Cancel、Status 等结构化命令 |
| API 访问边界 | executor 仅有 mock 与只读数据库执行器 | 建立服务端 Payment Gateway；由它保管凭据、限制 endpoint、校验输入、管理超时/重试和记录请求引用 |
| 确认语义 | 当前“确认方法”后直接执行只读查询 | 为资金动作单独定义 action review：付款方、收款人、金额、币种、汇率、费用、通道、风险、审批人、过期时间与一次性确认令牌 |
| 幂等与状态 | 没有 payment operation ID、幂等键或可恢复业务状态 | 持久化 `payment_draft / payment_operation`；提交使用 idempotency key；调用结果与支付状态分离 |
| 审批与限额 | 当前是查询确认，不绑定真实角色或金额策略 | Policy Engine 根据角色、组织、账户、币种、金额、国家和风险结果决定允许、确认或审批 |
| Webhook | 当前 API 没有支付 Webhook 接收和验签入口 | 验签、去重、按外部事件 ID 入库、推进付款状态机、重试和人工介入路径 |
| 审计与存储 | 目前主要是本地 JSON / JSONL，适合开发期 | 使用持久事件存储；记录 actor、策略版本、确认版本、幂等键、API request ID、Webhook event ID 和状态迁移 |
| 测试 | mock 数据用于查询，不是支付 API contract | 以沙盒 API 建立 contract、权限、幂等、重复 Webhook、失败恢复与审批回归测试 |

### 推荐的代码边界

不要把支付能力塞进现有 `MethodDraft(method_type="sql" | "code")` 或通用 executor。新增平行的支付领域模型：

```text
IntentProposal
  ├─ query_intent       → 现有 Schema / SQL / read-only flow
  └─ payment_intent     → PaymentCommandDraft

PaymentCommandDraft
  → PaymentGateway.validate / quote / submit / cancel / status
  → PaymentOperation（持久化状态机）
  → ActionReviewCard / ApprovalRequest
```

`PaymentCommandDraft` 至少应包含：操作类型、actor/组织/账户范围、引用的收款人 ID、金额与币种、目的、报价引用、风险与合规结果、幂等键、确认版本和过期时间。模型可填补或解释这些字段，但后端必须逐项验证；模型不得直接生成 HTTP URL、Header 或请求体。

### 开始沙盒接入的最小实施包

拿到 Chenyang 的商户沙盒后，先完成一次人工端到端走查，再实现以下最小切片：

1. **读取与引用**：以认证的测试商户身份列出付款账户和收款人；实现 `@收款人` 的后端解析，不信任模型自行命名或传 ID。
2. **草稿与报价**：用户说“给 `@SupplierA` 支付 3,000 USD”后，仅创建/更新付款草稿，调用校验与报价接口，不提交资金动作。
3. **支付确认卡**：展示最终付款账户、收款人、金额、币种、汇率、费用、预计到账、校验/合规结果与失效时间。
4. **沙盒提交**：确认后由 Payment Gateway 携带幂等键调用提交接口，写入 `submitted` 状态与外部 request/payment ID；重复点击不得重复提交。
5. **状态恢复**：通过查询和 Webhook 将状态更新为 `processing / completed / failed / cancelled`，并把失败原因转成可解释的下一步。

这一切片是可以开始做的：它复用现有确认卡和状态编排，却不会让查询 SQL 流程承担资金操作。前提是先拿到沙盒 API 的认证、权限模型、接口契约与完整支付生命周期。
